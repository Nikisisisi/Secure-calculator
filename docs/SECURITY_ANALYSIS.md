# Анализ безопасности Secure Calculator

Авторы: Nikita Obukhov & Daria Lapshina

Этот документ описывает результаты анализа безопасности проекта Secure Calculator, найденные проблемы, выполненные исправления и повторную проверку после исправлений.

---

## Используемые инструменты безопасности

В проекте используются следующие open-source инструменты:

| Инструмент | Назначение |
|---|---|
| Semgrep | Статический анализ исходного Python-кода |
| pip-audit | Поиск известных уязвимостей в Python-зависимостях |
| Gitleaks | Поиск секретов в Git-истории |
| Trivy | Проверка Docker-конфигурации и уязвимостей Docker-образа |

Все инструменты постепенно были интегрированы в GitHub Actions и используются как security gates перед выпуском новой версии приложения.

## 1. Неограниченная операция возведения в степень

### Обнаружение

Во время статического анализа исходного кода с помощью Semgrep было обнаружено, что endpoint:

```text
/calculate/power
```

использовал общую модель входных данных без ограничений на показатель степени.

Для проекта было создано собственное правило Semgrep:

```text
calculator-unbounded-power-operation
```

Оно было связано с риском неконтролируемого потребления ресурсов.

Результат до исправления:

```text
Semgrep findings: 1
```

### Риск

Неограниченные числовые входные данные могут привести к:

- чрезмерному потреблению вычислительных ресурсов;
- арифметическим ошибкам;
- нестабильному поведению приложения;
- снижению доступности API.

Проблема была классифицирована как связанная с:

```text
CWE-400: Uncontrolled Resource Consumption
OWASP API4:2023 Unrestricted Resource Consumption
```

### Исправление

Для операции возведения в степень была создана отдельная модель:

```text
PowerRequest
```

Для неё были установлены ограничения:

```text
основание: от -1 000 000 до 1 000 000
показатель степени: целое число от -20 до 20
```

Дополнительно была добавлена проверка, запрещающая:

```text
0 в отрицательной степени
```

Также были добавлены отдельные автоматические тесты для проверки этих ограничений.

### Проверка после исправления

После повторного запуска Semgrep:

```text
0 findings
```

Результат тестирования:

```text
14 passed
```

Таким образом, потенциально опасная операция была ограничена на уровне валидации входных данных, а исправление было подтверждено как статическим анализом, так и автоматическими тестами.

## 2. Запуск Docker-контейнера от root

### Обнаружение

При проверке конфигурации Docker с помощью Trivy была обнаружена проблема:

```text
DS-0002 HIGH
Specify at least 1 USER command in Dockerfile with non-root user as argument
```

Это означало, что приложение внутри контейнера запускалось от пользователя `root`.

### Риск

Запуск приложения с правами `root` увеличивает потенциальный ущерб в случае успешной атаки на приложение или контейнер.

Если злоумышленнику удастся использовать уязвимость приложения, работа процесса от непривилегированного пользователя ограничивает его возможности внутри контейнера.

### Исправление

В Dockerfile был создан отдельный системный пользователь:

```text
uid=10001(appuser)
```

После этого приложение запускается с помощью инструкции:

```dockerfile
USER appuser
```

### Проверка после исправления

Внутри работающего контейнера была выполнена команда:

```text
id
```

Результат:

```text
uid=10001(appuser) gid=999(appuser) groups=999(appuser)
```

После повторного анализа конфигурации Trivy:

```text
Misconfigurations: 0
```

Таким образом, приложение больше не запускается с правами `root`, а Docker-конфигурация успешно прошла повторную проверку Trivy.

## 3. Отсутствие Docker HEALTHCHECK

### Обнаружение

При анализе Dockerfile с помощью Trivy была обнаружена проблема:

```text
DS-0026 LOW
Add HEALTHCHECK instruction in your Dockerfile
```

В первоначальной версии Dockerfile отсутствовала встроенная проверка состояния приложения.

### Риск

Без `HEALTHCHECK` Docker может считать контейнер запущенным, даже если само приложение внутри него уже перестало корректно отвечать на запросы.

Это усложняет обнаружение проблем с доступностью сервиса.

### Исправление

В Dockerfile был добавлен `HEALTHCHECK`, который периодически проверяет endpoint:

```text
/health
```

Для проверки используется стандартная библиотека Python:

```text
urllib.request
```

Это позволяет не устанавливать дополнительные утилиты вроде `curl` и не увеличивать количество пакетов в production-образе.

### Проверка после исправления

После запуска контейнера Docker отображает состояние:

```text
healthy
```

Endpoint проверки состояния также возвращает:

```text
status = ok
```

После повторного анализа Dockerfile с помощью Trivy:

```text
Misconfigurations: 0
```

Таким образом, Docker теперь может автоматически контролировать работоспособность приложения внутри контейнера.

## 4. Уязвимые компоненты в production-образе

### Обнаружение

Первоначальное сканирование Docker-образа с помощью Trivy показало:

```text
Python vulnerabilities: 6
```

При дополнительном анализе было установлено, что некоторые найденные компоненты не являются зависимостями самого Secure Calculator.

Проверка:

```text
pip show msgpack setuptools urllib3
```

показала:

```text
Package(s) not found: msgpack, setuptools, urllib3
```

При этом внутри самого `pip` были обнаружены встроенные библиотеки:

```text
pip: 26.2.1
vendored msgpack: 1.1.2
vendored urllib3: 2.7.0
```

Таким образом, часть обнаруженных Trivy уязвимостей относилась к компонентам пакетного менеджера, а не к функциональности калькулятора.

### Риск

После установки зависимостей пакетный менеджер `pip` не требуется для работы production-приложения.

Наличие лишних компонентов в конечном Docker-образе:

- увеличивает поверхность атаки;
- увеличивает количество компонентов, которые необходимо контролировать;
- может приводить к появлению дополнительных CVE;
- позволяет выполнять ненужные для runtime операции установки пакетов.

### Исправление

Dockerfile был изменён таким образом, чтобы сначала установить необходимые зависимости, а затем удалить `pip` из production-образа.

После удаления была выполнена проверка:

```text
python -m pip --version
```

Результат:

```text
No module named pip
```

При этом приложение продолжило корректно работать.

### Проверка после исправления

До исправления:

```text
Python vulnerabilities: 6
```

После удаления ненужного пакетного менеджера:

```text
Python vulnerabilities: 0
```

Дополнительно было подтверждено:

```text
/health → ok
USER → appuser
HEALTHCHECK → healthy
```

Таким образом, ненужные для runtime компоненты были удалены из production-образа, а количество обнаруженных Trivy Python-уязвимостей уменьшилось с 6 до 0.

## 5. Лишние зависимости в production-образе

### Обнаружение

Первоначальный файл:

```text
requirements.txt
```

содержал одновременно как runtime-зависимости приложения, так и пакеты, необходимые только для тестирования и разработки.

Например:

```text
pytest
httpx
pluggy
iniconfig
Pygments
```

Эти пакеты не требуются для работы API в production.

В исходном production-образе находилось:

```text
22 Python distributions
```

### Риск

Каждая лишняя зависимость:

- увеличивает поверхность атаки;
- увеличивает размер и сложность Docker-образа;
- может содержать собственные уязвимости;
- требует дополнительного контроля и обновления.

### Исправление

Зависимости были разделены на два файла:

```text
requirements.txt
requirements-dev.txt
```

`requirements.txt` теперь содержит только runtime-зависимости приложения:

```text
fastapi==0.141.1
pydantic==2.13.5
uvicorn==0.53.0
```

`requirements-dev.txt` используется для тестов и разработки и включает:

```text
-r requirements.txt
httpx==0.28.1
pytest==9.1.1
```

Dockerfile устанавливает только:

```text
requirements.txt
```

поэтому тестовые и dev-зависимости не попадают в production-образ.

### Проверка после исправления

До минимизации:

```text
22 Python distributions
```

После минимизации:

```text
13 Python distributions
```

Количество Python-пакетов в production-образе уменьшилось на:

```text
9 пакетов (~41%)
```

При этом тесты продолжают успешно выполняться:

```text
14 passed
```

А Trivy показывает:

```text
Python vulnerabilities: 0
```

Таким образом, production-образ стал меньше по составу и содержит только те Python-зависимости, которые действительно нужны для работы приложения.

## 6. Уязвимость системного пакета Debian

### Обнаружение

Для Docker-образа была выполнена отдельная проверка Trivy с политикой:

```text
--severity HIGH,CRITICAL
--ignore-unfixed
```

Такая политика позволяет сосредоточиться на серьёзных уязвимостях, для которых уже существует доступное исправление.

В результате была обнаружена одна уязвимость:

```text
CVE-2026-103111
Package: libpcre2-8-0
Installed: 10.46-1~deb13u2
Fixed: 10.46-1~deb13u3
Severity: HIGH
```

### Риск

В production Docker-образе находился системный пакет Debian с известной уязвимостью уровня `HIGH`, для которой уже существовала исправленная версия.

Такую проблему можно считать практически устранимой, поэтому она должна блокировать выпуск новой версии приложения до исправления.

### Исправление

В Dockerfile было добавлено обновление системных пакетов:

```dockerfile
RUN apt-get update \
    && apt-get upgrade -y \
    && rm -rf /var/lib/apt/lists/*
```

После установки обновлений каталог:

```text
/var/lib/apt/lists/*
```

удаляется, чтобы не оставлять ненужные индексы пакетов в конечном Docker-образе.

Также при сборке образа в CI используется:

```text
docker build --pull
```

Это позволяет перед сборкой проверить наличие актуальной версии базового образа:

```text
python:3.13-slim
```

### Проверка после исправления

До исправления:

```text
Actionable HIGH/CRITICAL vulnerabilities: 1
```

После повторной сборки и сканирования:

```text
Actionable HIGH/CRITICAL vulnerabilities: 0
```

Для Python-зависимостей также было получено:

```text
Python vulnerabilities: 0
```

Важно: этот результат не означает, что в операционной системе полностью отсутствуют любые CVE.

Security Gate блокирует именно уязвимости уровней `HIGH` и `CRITICAL`, для которых уже существует доступное исправление.

Таким образом, обнаруженная исправимая системная уязвимость была устранена, а повторное сканирование Trivy подтвердило отсутствие подобных actionable findings.

## 7. Поиск секретов с помощью Gitleaks

### Обнаружение

Для проверки Git-истории проекта был использован инструмент Gitleaks.

Первоначальное сканирование показало:

```text
16 commits scanned
leaks found: 4
```

Все четыре срабатывания относились к правилу:

```text
generic-api-key
```

### Анализ

После изучения мест срабатывания было установлено, что все четыре finding находились внутри автоматически созданных JSON-отчётов Trivy.

В этих отчётах встречалось значение:

```text
GPG_KEY=7169605F62C751356D054A26A821E680E5FA6305
```

Это fingerprint публичного GPG-ключа из метаданных Docker-образа.

Он не является:

- паролем;
- API token;
- access token;
- приватным ключом;
- секретом аутентификации.

Поэтому данные срабатывания были классифицированы как false positive.

### Исправление

В проект был добавлен файл:

```text
.gitleaks.toml
```

Стандартные правила Gitleaks остались включёнными:

```toml
[extend]
useDefault = true
```

При этом было добавлено точечное исключение только для:

```text
правила generic-api-key
Trivy image JSON reports
GPG_KEY=<40 hexadecimal characters>
```

Таким образом, правило поиска секретов не было отключено глобально.

### Проверка после исправления

После добавления узкого allowlist:

```text
16 commits scanned
no leaks found
```

После добавления всех новых security-коммитов была выполнена дополнительная проверка всей Git-истории:

```text
20 commits scanned
2.54 MB scanned
no leaks found
```

Таким образом, false positive был корректно обработан, а проверка Gitleaks продолжает защищать репозиторий от случайной публикации реальных секретов.

## 8. Проверка Python-зависимостей с помощью pip-audit

### Обнаружение

Для проверки production Python-зависимостей был использован инструмент:

```text
pip-audit
```

Проверка выполнялась для файла:

```text
requirements.txt
```

Результат:

```text
No known vulnerabilities found
```

### Анализ

На момент проведения проверки известных уязвимостей в production-зависимостях проекта обнаружено не было.

Это означает, что текущий набор runtime-зависимостей не содержит известных уязвимостей, которые присутствуют в базе данных, используемой `pip-audit`.

### Интеграция в CI

Проверка `pip-audit` была добавлена в GitHub Actions.

Теперь при каждом push в ветку:

```text
main
```

выполняется автоматический аудит production-зависимостей.

Если `pip-audit` обнаружит известную уязвимость, шаг завершится с ошибкой и дальнейший выпуск новой версии будет остановлен.

Таким образом, проверка зависимостей выполняется автоматически и является частью Security Gate проекта.

## 9. Security Gates в CI/CD

После завершения локального анализа все основные инструменты безопасности были интегрированы в GitHub Actions.

Итоговая последовательность pipeline выглядит следующим образом:

```text
Checkout repository
        ↓
Python 3.13
        ↓
Install dependencies
        ↓
Candidate version bump
        ↓
pytest
        ↓
pip-audit
        ↓
Semgrep
        ↓
Gitleaks
        ↓
Trivy configuration scan
        ↓
Docker build --pull
        ↓
Trivy image vulnerability scan
        ↓
Commit new version
```

### Логика работы

Новая версия приложения сначала создаётся только внутри временного окружения GitHub Actions.

После этого запускаются:

- функциональные тесты;
- аудит Python-зависимостей;
- статический анализ кода;
- поиск секретов в Git-истории;
- проверка Docker-конфигурации;
- сборка Docker-образа;
- проверка уязвимостей собранного Docker-образа.

Только если все проверки проходят успешно, GitHub Actions выполняет commit новой версии.

### Используемые Security Gates

| Инструмент | Что проверяет |
|---|---|
| pytest | Корректность функциональности |
| pip-audit | Известные уязвимости Python-зависимостей |
| Semgrep | Потенциально небезопасные конструкции в исходном коде |
| Gitleaks | Секреты, токены и ключи в Git-истории |
| Trivy config | Ошибки конфигурации Dockerfile |
| Trivy image | Уязвимости ОС и компонентов Docker-образа |

Для Trivy image используется политика:

```text
--severity HIGH,CRITICAL
--ignore-unfixed
--exit-code 1
```

Это означает, что CI блокирует выпуск новой версии при наличии исправимой уязвимости уровня `HIGH` или `CRITICAL`.

### Проверка работы pipeline

После интеграции всех security-инструментов был выполнен реальный push в GitHub.

GitHub Actions успешно прошёл весь pipeline.

После успешного выполнения всех проверок автоматически была создана новая версия приложения:

```text
1.0.5
```

Commit:

```text
chore: bump version to 1.0.5
```

Таким образом, Security Gates работают не только локально, но и непосредственно в GitHub Actions.

## 10. Оставшиеся наблюдения

Во время запуска автоматических тестов появляются два предупреждения о deprecated API.

Первое предупреждение:

```text
StarletteDeprecationWarning:
Using httpx with starlette.testclient is deprecated; install httpx2 instead.
```

Второе предупреждение:

```text
DeprecationWarning:
The anyio.abc.BlockingPortal alias is deprecated
```

Эти предупреждения не являются подтверждёнными security-уязвимостями и не приводят к падению тестов.

На текущем этапе они рассматриваются как проблемы совместимости и сопровождения зависимостей.

В дальнейшем рекомендуется отслеживать обновления FastAPI, Starlette, httpx и AnyIO и устранять deprecated-интерфейсы при переходе на новые версии библиотек.

```text
  ↓
Enforce
```

Проект не ограничивался простым запуском автоматических сканеров.

- реальные проблемы исправлялись;
- false positive проверялись вручную;
- после исправлений выполнялось повторное сканирование;
- успешные проверки интегрировались в CI/CD как Security Gates.

- ограничена потенциально опасная операция возведения в степень;
- Docker-контейнер переведён на непривилегированного пользователя;

- удалён ненужный `pip` из production-образа;
- runtime и development зависимости разделены;
- количество Python-пакетов в production-образе уменьшено с 22 до 13;
- количество обнаруженных Python-уязвимостей уменьшено с 6 до 0;
- устранена исправимая системная уязвимость уровня HIGH;
- настроено сканирование Git-истории на секреты;
- добавлен аудит Python-зависимостей;
- Semgrep, pip-audit, Gitleaks и Trivy интегрированы в GitHub Actions.

Финальный Security Pipeline успешно прошёл на GitHub Actions и автоматически выпустил версию:

```text
1.0.5
```

Таким образом, Secure Calculator использует многоуровневый подход к безопасности, включающий анализ исходного кода, зависимостей, Git-истории, Docker-конфигурации и конечного Docker-образа.
